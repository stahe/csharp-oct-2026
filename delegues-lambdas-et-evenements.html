    7. Délégués, lambdas et événements

    Dans le cours de 2008, ce chapitre suivait celui consacré aux interfaces graphiques Windows Forms : les événements y étaient d'abord rencontrés sur les boutons et les formulaires, puis on apprenait à créer des événements dans ses propres classes. Le chapitre sur les interfaces graphiques a été retiré de cette version du cours. Nous partons donc directement de la notion qui est à la base de tout le mécanisme : le délégué, c'est-à-dire un objet qui référence une ou plusieurs méthodes. Tous les exemples sont des programmes console.

    Les délégués sont devenus en vingt ans l'un des outils les plus utilisés du langage. Leur écriture s'est considérablement allégée avec les expressions lambda (C# 3), que nous avons déjà utilisées sans les détailler avec LINQ au chapitre 5 : [Where(n => n > 5)] passe une lambda, donc un délégué, à la méthode [Where]. Ce chapitre explique ce qui se cache derrière cette écriture. Il se termine par les événements, qui reposent eux aussi sur les délégués. Les interfaces graphiques de .NET (Windows Forms, WPF, .NET MAUI) comme les frameworks web reposent sur ce mécanisme : un clic sur un bouton, l'arrivée d'une requête HTTP sont signalés à des méthodes abonnées.

    Les programmes du chapitre sont des applications fichier unique, dans le dossier [07-delegues]. On les exécute par [dotnet run delegues-NN.cs].

    7.1. Les types délégués prédéfinis

    7.1.1. La notion de délégué

    Un type délégué décrit un modèle (on dit aussi un prototype, ou une signature) de méthode : les types de ses paramètres et le type de son résultat. Une variable d'un type délégué peut alors référencer n'importe quelle méthode correspondant à ce modèle, et l'exécuter.

    Le framework .NET définit de nombreux types délégués. Le plus ancien est [EventHandler], utilisé par tous les événements dont nous parlerons en fin de chapitre. Il est défini ainsi :

    1
    public delegate void EventHandler(object? sender, EventArgs e);

    Le mot clé [delegate] fait de [EventHandler] un type délégué. Ce type désigne un modèle de méthode :

    • ayant pour 1er paramètre un objet de type [object?] (l'objet à l'origine de l'événement, éventuellement [null]) ;
    • ayant pour 2e paramètre un objet de type [EventArgs] (les informations sur l'événement) ;
    • ne rendant aucun résultat ([void]).

    Une méthode correspondant au modèle défini par [EventHandler] pourrait être la suivante :

    1
    static void Afficher(object? sender, EventArgs e) { ... }

    Pour créer un objet de type [EventHandler] qui référence cette méthode, on peut écrire :

    1
    EventHandler gestionnaire = new EventHandler(Afficher);

    ou, plus simplement :

    1
    EventHandler gestionnaire = Afficher;

    Dans cette seconde écriture, le nom de méthode [Afficher] (un groupe de méthodes, car une méthode peut avoir plusieurs surcharges) est converti automatiquement par le compilateur en un objet [EventHandler] : c'est la conversion de groupe de méthodes, possible depuis C# 2. Le compilateur choisit, parmi les surcharges de [Afficher], celle qui correspond à la signature du délégué. On exécute ensuite le délégué comme une méthode : [gestionnaire("programme", EventArgs.Empty)].

    7.1.2. Les délégués génériques Func, Action et Predicate

    Avant les génériques (C# 2), il fallait définir un type délégué pour chaque signature de méthode. Le framework fournit aujourd'hui des types délégués génériques qui couvrent la quasi-totalité des besoins :

    Type délégué
    Méthodes référencées
    [Action]
    aucun paramètre, aucun résultat : [void M()]
    [Action<T1, ..., T16>]
    1 à 16 paramètres, aucun résultat : [void M(T1 p1, ...)]
    [Func<TResult>]
    aucun paramètre, un résultat : [TResult M()]
    [Func<T1, ..., T16, TResult>]
    1 à 16 paramètres, un résultat de type [TResult] (toujours le dernier type)
    [Predicate<T>]
    un paramètre, un résultat booléen : [bool M(T p)]
    [Comparison<T>]
    deux paramètres de même type, un résultat entier : [int M(T x, T y)]

    [Predicate<T>] et [Func<T, bool>] décrivent la même signature mais ce sont deux types différents : [Predicate<T>] date de .NET 2 et est utilisé par les méthodes de [List<T>] et de [Array] ([FindAll], [RemoveAll], [Exists]…), tandis que LINQ, apparu avec .NET 3.5, utilise [Func<T, bool>].

    7.2. Définir des types délégués

    Les types prédéfinis suffisent souvent, mais on peut définir ses propres types délégués. L'instruction :

    1
    public delegate int Operation(int n1, int n2);

    définit un type appelé [Operation] qui représente un modèle de méthode acceptant deux entiers et rendant un entier. Par rapport à [Func<int, int, int>], le type [Operation] a un nom qui dit à quoi il sert, et ses paramètres ont des noms ([n1], [n2]) que les outils de développement affichent.

    Une variable [op] de type [Operation] a pour rôle d'enregistrer une liste de méthodes correspondant au modèle [Operation] : on parle de délégué multicast.

    • l'enregistrement d'une méthode [f] dans la variable [op] se fait par [op = new Operation(f)] ou plus simplement par [op = f] ;
    • pour ajouter une méthode [g] à la liste des méthodes déjà enregistrées, on écrit [op += g] ;
    • pour enlever une méthode [h] déjà enregistrée, on écrit [op -= h] ;
    • l'instruction [n = op(n1, n2)] exécute, dans l'ordre d'enregistrement, toutes les méthodes enregistrées dans [op], avec les paramètres [n1] et [n2]. Le résultat [n] récupéré est celui de la dernière méthode exécutée.

    Le cours de 2008 indiquait qu'il n'est pas possible d'obtenir les résultats de toutes les méthodes. C'est possible, mais pas avec un simple appel : il faut parcourir la liste des méthodes, rendue par [GetInvocationList], et les appeler une à une. En pratique, les méthodes enregistrées dans un délégué multicast rendent le plus souvent [void].

Operation? vide = reste - c1.Ajouter;
Console.WriteLine($"vide est null : {vide is null}");

Console.WriteLine($"vide?.Invoke(1, 1)={vide?.Invoke(1, 1)}");

L'interpolation de chaîne affiche [null] comme une chaîne vide. Nous retrouverons cette écriture avec les événements.

    Un délégué est un objet immuable : les opérations [+] et [-] (et donc [+=] et [-=]) ne modifient pas le délégué existant, elles en créent un nouveau. Cette propriété aura son importance pour les événements.

    • lignes 4-6 : une méthode anonyme. Le mot clé [delegate] est suivi de la liste des paramètres et du corps de la méthode. Le compilateur génère une méthode (avec un nom qu'il choisit) et crée un délégué [Func<int, int, int>] qui la référence.     • ligne 18 : les types des paramètres ont disparu. Le compilateur les déduit du type délégué cible [Func<int, int, int>] : [n1] et [n2] sont de type [int]. Le corps est réduit à une expression, dont la valeur est le résultat de la lambda : c'est une lambda à corps d'expression (expression lambda). C'est la forme la plus courante ;
    • ligne 22 : avec un seul paramètre dont le type n'est pas précisé, les parenthèses sont facultatives. [x => x * x] se lit « x donne x fois x ». Ligne 23, la même lambda d'un paramètre, de type [string], rend un booléen : c'est un [Predicate<string>] ;
    • lignes 27-28 : sans paramètre, on écrit des parenthèses vides. Une lambda dont le corps est un appel de méthode [void] convient à un délégué [Action] ;
    • lignes 33-39 : une lambda à corps de bloc peut contenir n'importe quelles instructions : déclarations, boucles, tests… ;
    • ligne 44 : le caractère de soulignement [_] désigne un paramètre ignoré (discard, C# 9). On l'utilise quand la signature du délégué impose des paramètres dont la lambda n'a pas besoin, ce qui est fréquent pour les gestionnaires d'événements ;
    • ligne 49 : l'usage le plus fréquent des lambdas consiste à les passer directement en paramètre d'une méthode qui attend un délégué. Comparez avec [delegues-01.cs] : il n'est plus nécessaire d'écrire une méthode [EstPair] ;
    • ligne 50 : une lambda de type [Comparison<int>] qui inverse la comparaison usuelle : la liste est triée par ordre décroissant.

    Forme
    Exemple
    paramètres typés, corps de bloc
    [(int a, int b) => { return a + b; }]
    paramètres non typés, corps d'expression

    7.5. Gestion d'événements

    7.5.1. Le modèle des événements .NET

    Les délégués servent à définir des événements. Une classe [C1] peut définir un événement [Evt1] de la façon suivante :

    • un type délégué est défini dans ou en dehors de la classe [C1] :
    1
    delegate void Evt(T1 param1, T2 param2, ...);
    • la classe [C1] définit un champ de ce type délégué :
    1
    public Evt? Evt1;
    • lorsqu'une instance [c1] de la classe [C1] veut signaler un événement, elle exécute son délégué [Evt1] en lui passant les paramètres définis par le type [Evt]. Toutes les méthodes enregistrées dans le délégué [Evt1] sont alors exécutées avec ces paramètres. On peut dire qu'elles ont été averties de l'événement [Evt1] ;
    • si un objet [c2] utilisant l'objet [c1] veut être averti de l'événement [Evt1] de l'objet [c1], il enregistre l'une de ses méthodes [c2.M] dans le délégué [c1.Evt1]. Sa méthode [c2.M] sera alors exécutée chaque fois que l'événement [Evt1] se produira sur l'objet [c1]. Il pourra également se désinscrire lorsqu'il ne voudra plus être averti ;
    • comme le délégué [c1.Evt1] peut enregistrer plusieurs méthodes, différents objets [ci] peuvent s'enregistrer auprès de [c1.Evt1] pour être prévenus de l'événement.

    Dans ce scénario, on a :

    • une classe qui signale (on dit aussi publie, ou émet) un événement ;
    • des classes qui sont averties de cet événement. On dit qu'elles souscrivent, ou s'abonnent, à l'événement ;
    • un type délégué qui définit la signature des méthodes qui seront averties de l'événement. Ces méthodes sont appelées gestionnaires d'événement (event handlers).

    C'est le patron de conception Observateur (Observer) : l'émetteur ne connaît pas ses abonnés, il se contente de les avertir.

    Le framework .NET définit une signature standard pour le délégué d'un événement :

    1
    public delegate void MonEventHandler(object? sender, EventArgs e);
    • [sender] : l'objet qui a signalé l'événement ;
    • [e] : un objet de type [EventArgs] ou dérivé, qui apporte des informations sur l'événement ;
    • par convention, le nom du type délégué se termine par [EventHandler].

    Il définit également une façon standard de déclarer un événement de type [MonEventHandler] dans une classe :

    Le champ [Evt1] est de type délégué. Le mot clé [event] restreint les opérations qu'on peut faire sur lui :

    • de l'extérieur de la classe [C1], seules les opérations [+=] et [-=] sont possibles. Cela empêche de remplacer ou d'effacer (par erreur, par exemple en écrivant [=] au lieu de [+=]) les méthodes abonnées par d'autres objets. On peut seulement s'abonner ([+=]) ou se désabonner ([-=]) ;
    • seule la classe [C1] peut exécuter le délégué, c'est-à-dire déclencher l'événement : [Evt1?.Invoke(this, e)].

    Si l'on essaie, de l'extérieur de la classe, d'écrire [c1.Evt1 = null;] ou [c1.Evt1(null, EventArgs.Empty);], le compilateur répond : [error CS0070: L'événement 'C1.Evt1' ne peut apparaître qu'à gauche de += ou -= (sauf quand il est utilisé à partir du type 'C1')] (en anglais : [The event 'C1.Evt1' can only appear on the left hand side of += or -= (except when used from within the type 'C1')]).

    Plutôt que de définir un type délégué pour chaque événement, on utilise le délégué générique prédéfini :

    1
    public delegate void EventHandler<TEventArgs>(object? sender, TEventArgs e);

    Le type [TEventArgs] est celui du second paramètre, l'objet qui décrit l'événement. Avec ce délégué générique, la déclaration d'un événement [X] dans une classe [C] suit le schéma conseillé suivant :

    • définir un type [XEventArgs] dérivé de [EventArgs] pour encapsuler les informations sur l'événement [X] ;
    • définir dans la classe [C] un événement de type [EventHandler<XEventArgs>] ;
    • définir dans la classe [C] une méthode protégée et virtuelle [protected virtual void OnX(XEventArgs e)] destinée à publier l'événement [X] aux abonnés. Elle est virtuelle pour qu'une classe dérivée puisse modifier la façon dont l'événement est publié.

    En 2008, le type [TEventArgs] devait obligatoirement dériver de [EventArgs] (contrainte [where TEventArgs : EventArgs]). Cette contrainte a été supprimée dans .NET Framework 4.5 : n'importe quel type convient, y compris un [record]. On continue cependant, par convention, à dériver de [EventArgs]. Notons qu'un [record] ne peut pas dériver de [EventArgs] : un [record] ne peut hériter que d'un autre [record] (erreur [CS8864 : Les enregistrements peuvent uniquement hériter d'un objet ou d'un autre enregistrement]). Nous utiliserons donc une classe ordinaire.

public static class Outils
{
    // filtre une séquence avec un prédicat : l'équivalent de Where
    public static IEnumerable<T> Filtrer<T>(IEnumerable<T> source, Func<T, bool> predicat)
    {
        foreach (T element in source)
        {
            if (predicat(element))
            {
                // l'élément est rendu à l'appelant ; le parcours reprendra ici
                yield return element;
            }
        }
    }
}

public static class Extensions
{
    // membres d'extension (C# 14) de IEnumerable<T>
    extension<T>(IEnumerable<T> source)
    {
        // Filtrer comme méthode d'extension : on réutilise Outils.Filtrer
        public IEnumerable<T> Filtrer(Func<T, bool> predicat) => Outils.Filtrer(source, predicat);

        // transforme chaque élément : l'équivalent de Select
        public IEnumerable<TResult> Transformer<TResult>(Func<T, TResult> transformation)
        {
            foreach (T element in source)
            {
                yield return transformation(element);
            }
        }
    }
}

    {
        case BinaryExpression binaire:
            // opération à deux opérandes : &&, >, ==, %...
            Console.WriteLine($"{marge}{binaire.NodeType}");
            Afficher(binaire.Left, niveau + 1);
            Afficher(binaire.Right, niveau + 1);
            break;
        case ParameterExpression parametre:
            Console.WriteLine($"{marge}Parameter {parametre.Name}");
            break;
        case ConstantExpression constante:
            Console.WriteLine($"{marge}Constant {constante.Value}");
            break;
        default:
            Console.WriteLine($"{marge}{noeud.NodeType} {noeud}");
            break;
    }
}

    À quoi cela sert-il ? Un délégué ne peut qu'être exécuté, dans le programme. Un arbre d'expression peut être analysé et traduit dans un autre langage. C'est ce que fait Entity Framework Core, que nous étudierons au chapitre 11. Quand on écrit une requête LINQ sur une table de base de données, par exemple [contexte.Tranches.Where(t => t.Limite > 20000)], la méthode [Where] utilisée n'est pas celle de [IEnumerable<T>] mais celle de [IQueryable<T>], dont le paramètre est un [Expression<Func<T, bool>>]. EF Core parcourt cet arbre, comme notre méthode [Afficher], et le traduit en une clause SQL [WHERE Limite > 20000] exécutée par le serveur de bases de données. La même lambda, écrite de la même façon, devient ainsi soit du code .NET, soit du SQL, selon le type du paramètre qui la reçoit.

    7.8. Conclusion

    Nous retiendrons de ce chapitre :

    • un délégué est un objet qui référence une ou plusieurs méthodes d'une signature donnée. Les types prédéfinis [Func<>], [Action<>] et [Predicate<T>] dispensent le plus souvent de définir ses propres types délégués ;
    • les expressions lambda permettent d'écrire la méthode à l'endroit même où l'on crée le délégué. Elles capturent les variables qui les entourent (attention aux boucles [for]) ;
    • un délégué peut remplacer une interface à une seule méthode, avec plus de souplesse ;
    • un événement est un délégué protégé par le mot clé [event] : on s'y abonne par [+=], on s'en désabonne par [-=], et seule la classe qui le déclare le déclenche, par [Evt?.Invoke(this, e)] ;
    • LINQ est construit sur des méthodes qui reçoivent des délégués, et EF Core sur des arbres d'expression.

    Les délégués reviendront dans les chapitres suivants : une tâche ([Task.Run]) exécute un délégué dans un autre thread (chapitres 8 et 9), et les services web ASP.NET Core associent des lambdas aux adresses HTTP (chapitre 13).
